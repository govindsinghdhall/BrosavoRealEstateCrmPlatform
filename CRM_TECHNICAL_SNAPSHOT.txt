5. MULTI-TENANT ARCHITECTURE
================================================================================

Separation key: organizationId (numeric), NOT company_id / tenantId.

How logged-in user's organization is determined:
1. User registers/logs in via /auth
2. JWT signed with JwtPayload { userId, organizationId, roleId, email } (src/utils/jwt.ts)
3. Frontend stores accessToken; axios sends Authorization: Bearer <token>
4. authenticate middleware verifies JWT and sets req.auth
5. Controllers use req.auth.organizationId for all queries

Organization ID handling:
- Embedded in JWT — clients do not send organizationId in body for normal CRM ops
- Services accept organizationId as first argument

Tenant isolation in queries:
- Pattern: Contact.findOne({ _id, ...activeOrgFilter(organizationId) })
- activeOrgFilter = { organizationId, deletedAt: null } (src/utils/pagination.ts)
- Role permission check also scoped: Role.findOne({ _id: roleId, organizationId })

Contacts belong to organizations via Contact.organizationId
Users belong to organizations via User.organizationId
WhatsApp accounts/campaigns/messages scoped by organizationId

Middleware for tenant isolation: no separate "tenant middleware"; tenancy is JWT organizationId + query filters.

Authorization: requirePermission(...permission strings) against Role.permissions.

Example (contacts list):
  listContacts(req.auth.organizationId, { page, limit, search, ... })

WhatsApp OAuth state encodes organizationId (base64 JSON) for callback association.

CRITICAL for WhatsApp/campaigns/contacts: always scope by req.auth.organizationId; never trust client-supplied org ids.

25. POTENTIAL CONFLICTS
================================================================================

1. Two campaign systems: MarketingCampaign vs WhatsAppCampaign — frontend WhatsAppTab currently uses marketing campaign status vocabulary.
2. Two template systems: WhatsAppTemplate (local message) vs WhatsAppMetaTemplate (Meta approved) — campaigns need Meta templates.
3. Legacy whatsapp.controller/service vs WhatsAppController/WhatsAppService — risk of editing the wrong file.
4. Organization.settings.whatsapp vs WhatsAppAccount model — dual configuration sources.
5. WhatsApp cron not started — queued campaigns may never send.
6. No Redis/Bull — large blasts inside HTTP request will timeout/rate-limit against Meta.
7. Phone exact-match duplicates — Google import formats (+91 vs 91 vs 0-prefixed) will create duplicates unless normalized.
8. Contact.phone not unique at DB level — race conditions possible on concurrent imports.
9. Frontend ENDPOINTS.WHATSAPP incomplete vs backend routes.
10. Vite proxy targets :4000 while backend env default PORT 3000 and api client default :3000 — local port confusion.
11. Frontend package scripts --prefix RealEstateBackend assume nested folder; actual backend is sibling Desktop path.
12. WhatsApp routes lack requirePermission — any authenticated role could hit campaigns if UI exposed.
13. businessId unique globally on WhatsAppAccount — one Meta business cannot connect to two orgs.
14. Numeric IDs everywhere — do not introduce ObjectId for new related models without strong reason.
15. env.ts does not validate all WHATSAPP_* / ENCRYPTION_KEY vars — misconfig fails late at runtime.
